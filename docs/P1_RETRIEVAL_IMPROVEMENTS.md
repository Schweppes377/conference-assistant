# P1: улучшение нормативного поиска и отбора контекста

Дата: 14.10.2026. Версия алгоритма: `p1-3`. Основание — `NORMATIVE_ANSWER_QUALITY_AUDIT.md` и результаты P0. Приведённые показатели характеризуют поиск, а не правильность будущих ответов GigaChat.

## 1. Причины проблем исходного алгоритма

- **Кладовые, ISSUE_003:** специальный пункт 6.2.2.14 СП 54 находился среди сохранённых кандидатов на местах 10–11. Бонус плотности совпадений составлял 0,35 общей оценки и поощрял широкие фрагменты с несколькими общими словами. Отбор первых пяти исключал специальное требование, хотя оба semantic scores превышали 0,84. Бюджет текста не был причиной потери.
- **Высота выхода, ISSUE_004:** п. 4.2.18 СП 1 отсутствовал среди сохранённых 20 результатов. Первоначальные выдачи и запрос, который нашёл каждый результат, не сохранялись, поэтому нельзя доказать, потерялся ли пункт на semantic search или при усечении объединённого списка. Разговорные search_terms и слабо связанные расширения были дополнительным риском.
- **Шум, ISSUE_007:** прямой п. 7.26 о смежности шахты лифта и жилой комнаты находился на месте 7 и не попал в LLM. Вместо него передавались определения/формулы и типы квартир.
- **МГН, ISSUE_006:** ключевые слова, оглавление и список ссылок имели высокую оценку совпадений. Старый алгоритм не различал тематический список и нормативное положение; требования внутренних путей вытесняли положения о входах.

Максимум cosine score по расширенным запросам не означал применимость к исходному вопросу. Дедупликация по file/page/chunk_index устраняла повторы одного ID, но не повторные по содержанию фрагменты. Ограничение символов проверялось с прекращением всего отбора при первом слишком большом chunk; менее объёмные последующие chunks не рассматривались.

## 3. Новый алгоритм

### Подготовка запросов

Нормализованный вопрос всегда сохраняется целиком. Из search_terms удаляется разговорная оболочка; техническое содержание остаётся. Простая нормализация русских окончаний и раздельного «вне квартирные» используется только как поисковый сигнал. Она не является полноценным морфологическим или семантическим анализатором.

Количество запросов ограничено восемью. Отдельный параметр «высота», «ширина» или «толщина» при наличии объекта используется в сочетании с объектом, а не как самостоятельный поисковый запрос. Варианты терминов — небольшой прозрачный словарь, например дверь эвакуационного выхода / эвакуационный выход и вентиляционный канал / воздуховод. Варианты расширяют recall; они не доказывают взаимозаменяемость объектов или правомерность применения нормы. Ни reference sources, ни известные chunk IDs, ни нормативные числа для восьми тем не участвуют в построении запросов.

### Получение кандидатов

Для каждого запроса E5 вызывается один раз. К semantic TOP-20 добавляются максимум 20 lexical candidates из текстов **того же существующего Chroma-корпуса**. Lexical ranking использует совпадение нормализованных терминов с inverse document frequency, без бонуса за многократное повторение слова. Для этих кандидатов cosine вычисляется по исходным сохранённым vectors и query vector; keyword score не подставляется вместо semantic score.

Результаты объединяются по файлу, странице и chunk_index. Сохраняются все origins: запрос, метод, исходная позиция, cosine score/distance и lexical score. Максимум semantic score по запросам сохранён для совместимости, но теперь он сопровождается всеми исходными значениями и не рассматривается как доказательство применимости.

### Переранжирование

Базовая сумма: 0,35 semantic + 0,30 совпадение объекта + 0,20 параметра + 0,10 нормативной формулировки + 0,05 области. Прежнего бонуса detail density нет. Сигналы объекта и параметра оцениваются в компактных участках текста; составной уточнённый термин сопоставляется совместно. Повторение одних слов и большая длина сами по себе не дают бонус. Сохранённые таблицы рассматриваются целиком как один существующий chunk.

Publication/contents/references/title получают penalty 0,8 и не включаются как основания. Definitions получают penalty 0,2, если вопрос не запрашивает определение. Для явно отличающейся области есть мягкий penalty 0,15, например текст о силосах при вопросе о многоквартирном доме; документ целиком не запрещается. Классификация эвристическая и может пропускать служебные фрагменты или неверно распознавать смешанные страницы.

Сохраняются компоненты оценки и trace всех объединённых кандидатов, включая отброшенные после 20-го места. `rerank_score` остаётся поисковой оценкой, а не вероятностью нормативной правильности.

### Контекст и связанные положения

Первый chunk — лучший допустимый по relevance; остальные выбираются с учётом прироста покрытия аспектов, неповторяемости и небольшого бонуса разнообразия документов. Нормы с разными числами, пунктами и признаками исключений не удаляются как near-duplicates. Исключённый по бюджету chunk не останавливает проверку следующих.

При явной ссылке включённого родительского основания допускается получение до двух существующих chunks того же файла, содержащих указанный пункт/таблицу. Номер извлекается из исходного текста, не генерируется. Междокументная квалифицированная ссылка не считается локальной. Соседняя страница другого документа не присоединяется. Нет рекурсивного обхода, целых документов или новых PDF-фрагментов.

Связанные chunks добавляются к 20 обычным кандидатам как отдельные дополнительные основания, поэтому список candidates может содержать до 22 элементов. Их SOURCE ID не меняет уже присвоенные IDs. Сохраняются точный текст, file/page/chunk, parent chunk, исходная ссылка, query и собственный cosine, если он рассчитан; при наследовании оценки это явно отмечено в trace. Дополнительного E5-кодирования для связанного chunk не требуется.

Ссылочное положение может занять следующий слот после своего включённого parent. К нему не применяется независимый порог cosine 0,84, если parent уже включён: необходимость такого текста определяется явной связью. Это не удостоверение его смысловой применимости. **Слишком сильный приоритет связанного контекста остаётся одним из выявленных ограничений**, поскольку способен вытеснить прямой ответ на другой аспект.

Общий лимит остался **5 chunks / 12000 символов user prompt**. Chunks не обрезаются и не переписываются. Token/output limits и число LLM retries не увеличены. Покрытие аспектов вычисляется лексически, не выдаётся за независимую смысловую оценку полноты.

### P0 и обратная совместимость

SourceEvidence, PreparedQuestion, QAResult и AnalyzedIssue получили только необязательные поля с defaults. Старые JSON читаются без миграции; старый resume использует свой сохранённый контекст без скрытого повторного retrieval. Версия checkpoint и QAConfig не менялись. Поэтому resume старого эксперимента сам по себе не применит P1 к уже сохранённым retrieval results: для нового сравнения явно вызывается prepare по сохранённым вопросам.

Проверки SOURCE, дословных выдержек, чисел и отсутствия автоматического подтверждения соответствия из P0 сохранены. Trace пишется в JSON/checkpoint, а не в пользовательский Markdown. Формулы оценок WER/CER/DER/F1/Hit@K/MRR и существующие пороги matching не менялись.

## 4. Методика сравнения и происхождение эталона

Baseline — полный сохранённый запуск **8 октября 2026**, `construction_meeting_20261008_174708_218282_analysis.json`, с соответствующим progress. Исходные candidates/context и времена зафиксированы до изменения алгоритма в `P1_BASELINE.json`.

Использован неизменённый `evaluation/datasets/construction_meeting.json`: verification.status=verified, дата подтверждения 5 октября. Все **19 expected_sources** найдены в существующем индексе; их indexed_text_sha256 совпали. Reference sources использованы только при оценке после поиска. Matcher mode=text, threshold=0,2 и функция evaluation.metrics.retrieval_metrics остались прежними; все восемь вопросов сопоставились.

Метрики требуют точной identity из эталона: designation/document и указанные page/chunk. Поэтому unlisted нормативно допустимый альтернативный пункт не считается hit. Например, baseline лестницы уже содержал СП 1, таблицу 4 на PDF с. 20, но этот альтернативный chunk не входит в expected_sources. Нулевой hit здесь не означает, что baseline не нашёл никакой правильной нормы. Hit также не доказывает соблюдение условий и полноту составного вопроса.

Выполнена реальная локальная retrieval-проверка на тех же восьми normalized_question/search_terms, с E5 из существующего cache и **копией исходного индекса**. Сеть заблокирована на socket.connect, HF/Transformers offline, GigaChat client не создавался, аудио не обрабатывалось. Embedding device — CUDA; индекс содержит 3787 chunks. Исходный индекс и PDF не менялись.

Веса и пороги изначально заданы по синтетическим случаям. Первые контрольные проверки выявили функциональные дефекты: изолированный параметр, потерю ссылочного условия, вытеснение сильного основания общими словами. Их исправления проверены синтетическими тестами; веса базовой суммы не подбирались по восьми вопросам. **Однако алгоритмические признаки и отбор уточнялись после просмотра этих результатов, поэтому восемь вопросов уже не являются неизвестным holdout.** Сравнение воспроизводимо как regression/development experiment; для независимой оценки обобщения нужны другие записи/вопросы. Эталон не менялся, все промежуточные результаты сохранены.

Знаменатель — восемь сопоставленных вопросов. MRR candidates относится к сохранённому ограниченному списку: до 20 reranked результатов и до двух дополнительных связанных chunks в конце; это не ранг во всём корпусе. MRR context относится к фактическому порядку пяти выбранных источников.

В контексте эталон есть у 6/8 вместо 3/8. В первых пяти candidates — у 7/8 вместо 3/8; хотя у всех восьми есть хотя бы один эталон где-то среди сохранённых candidates, это не гарантирует передачу модели.

|---|---:|---:|
| Автоматически распознанные служебные chunks из 40 | 2 | 0 |

Автоматическая доля служебных chunks: 5% → 0%. Аудит вручную определял три служебных фрагмента в ISSUE_006, тогда как текущая эвристика baseline распознаёт только два. Поэтому ноль нового детектора не равен независимо подтверждённому отсутствию служебных/неподходящих chunks. Общее количество по смыслу нерелевантных нормативных фрагментов не измерено: для них нет полной независимой разметки. Ноль near-duplicate pairs также не означает отсутствие частичного повторения отдельных требований.

TOP_K=5, candidate depth=20, linked limit=2, context limit=12000. Реально измеренные user prompts: 6261–6872 символов. Это не точное количество токенов GigaChat; API не вызывался, token-cost не измерялся.

## 7. Улучшения, ограничения и следующие действия

Улучшились попадание специального пункта кладовых и ограничения смежности шахты с жилой комнатой, отбор полной таблицы лестниц относительно зафиксированного эталона и наличие связанных условий вентиляционной системы. В окончательном контексте вентиляции есть СП 54, п. 9.12, СП 60, п. 7.1.9 и связанные 7.11.17–7.11.18. Полнота нормативного ответа GigaChat этим не измерялась.

Прямая норма высоты выхода теперь найдена и сохранена среди 20 кандидатов, но **не вошла в финальный контекст**. Для входа МГН обнаружены 5.1.14 и 6.1.1–6.1.2, однако они тоже не выбраны; 6.1.2–6.1.3 и таблица наружных пандусов остаются за пределами 20. Таким образом, проблемы 004 и 006 не устранены полностью. У освещения нужные основания сохранены, но первое эталонное основание оказалось на позиции 4 вместо позиции 1 baseline; это ухудшение приоритета.

Следующий приоритет — различать аспект основного нормативного требования и поясняющие ссылки так, чтобы ссылки не занимали слоты вместо прямого ответа. Нужна отдельная проверочная подборка составных вопросов с размеченной областью применения; на ней следует измерить сохранение каждого аспекта, а не только any-hit. После этого — работа с областью «вход/наружный пандус/внутренний путь», качеством связанных пунктов и служебных смешанных страниц. Не следует закреплять результаты восьми тем правилами их chunk IDs или увеличивать количество LLM-генераций.

**Полный контрольный запуск с GigaChat пока не рекомендован:** при 004 и 006 модель всё ещё не получает нужные основания. Сначала требуется устранить эти потери финального отбора. После локальной проверки можно отдельно разрешить текстовый RAG → GigaChat regression по сохранённым вопросам; повторный ASR/diarization для такой проверки не нужен.

## 8. Воспроизведение

Тесты из корня проекта, с отдельным новым результатом:

```powershell
.\run-direct.ps1 -m pytest -q --reliability-output=docs/P1_TEST_RESULTS.json
```

Во время задачи выполнялась стандартная `.\run-direct.ps1 -m pytest -q`; путь reliability-output передавался в окружении только этого запуска, чтобы не перезаписать исторический reliability.json.

Повторить локальное сравнение на использованной копии индекса (выходной файл должен быть новым):

```powershell
.\run-direct.ps1 -m evaluation.p1_compare --persist-dir "C:\Users\maree\.codex\.chatgpt-projects\g-p-6aac4ce0dfa481918d8d3743aa7c1d1d\p1_index_snapshot" --output evaluation\results\p1_repeat.json
```

Никакого GigaChat или audio inference эта команда не выполняет. Cache embedding-модели должен уже существовать; сеть заблокирована. Путь snapshot — вспомогательная копия для этого эксперимента. При удалении/переносе workspace следует создать другую копию существующего data/chroma и явно указать её; переиндексация не требуется.

## 9. Артефакты и границы доказательства

- `P1_RETRIEVAL_COMPARISON.json` — итоговые queries, полный trace, кандидаты, точные контексты, результаты неизменённого evaluator, timings и hashes входных артефактов.
- `P1_BASELINE.json` — сохранённый baseline до изменений.
- `P1_PARAMETERS.json` — версия, веса и hashes файлов алгоритма, зафиксированные перед итоговым retrieval.
- `P1_TEST_RESULTS.json` — локальный pytest, без API.
- `P1_RETRIEVAL_EXPERIMENT_1.json`, `P1_RETRIEVAL_EXPERIMENT_2.json`, `P1_RETRIEVAL_BEFORE_OPTIMIZATION.json` — промежуточные измерения, включая ухудшения; они не удалены.

205 защищённых файлов проверены по SHA-256 после задачи: изменений нет. В эту проверку вошли оригинальный Chroma, data/results, PDF, reference data, прежние evaluation/results, detector, GigaChatClient и ключевые P0-файлы. Новые результаты созданы отдельно.

Не установлены этим экспериментом: точность новых ответов LLM, юридическая актуальность редакций, полная применимость найденных требований, независимая экспертная precision каждого нового chunk, независимость восьми вопросов после итераций, ускорение всего end-to-end приложения. Простой lexical/rerank score не удостоверяет эти свойства. P0 продолжает явно ограничивать неподтверждённые выводы.
