## 2. Исправленные дефекты и фактическое поведение

### Ссылки

Разбираются `[SOURCE_1]`, `[ SOURCE_1 ]`, `[SOURCE_1, SOURCE_3]` и соседние одиночные ссылки. Сохраняется порядок первого цитирования, повторы удаляются. Неизвестный ID в группе отклоняется; ошибочное оформление ссылки не позволяет скрыть ID от проверки.

В Markdown основания обозначаются собственными `[SOURCE_N]`, без переименования по порядку списка. Поэтому первым показанным основанием может быть SOURCE_2 — это остаётся SOURCE_2. Номер пункта печатается, если он указан в обосновании и обнаружен как заголовок/явная ссылка в дословной выдержке; иначе выводится «не установлен». Само число `1.05 м` не считается пунктом `1.05`.

### Проектные и нормативные значения

Проектные факты содержат выдержку из исходного вопроса и точность `exact / approximate / unknown`. Search_terms продолжают участвовать в прежнем поиске, но больше не доказывают факты проекта при валидации ответа. При «около», «примерно» и аналогичных указаниях факт не становится точным даже при пропуске этого слова моделью в короткой выдержке.

Для нового JSON-обоснования нормативное значение должно находиться в выдержке конкретного требования, связанного с конкретным SOURCE; проектное — в выдержке конкретного проектного факта. Значение из другого требования или другого кандидата не подставляется. Конверсия длины/площади и Decimal сохранены. Размерности должны совпадать.

Для старого свободного текста числовая проверка связывает участок перед ссылкой с этой ссылкой/группой, а не со всеми источниками ответа. Нормативное значение в конце без ссылки не заимствуется из ранее процитированного chunk. Явно обозначенный минимум/максимум не разрешается только из-за совпадения с проектным числом. Это ограниченная синтаксическая защита; её успешность сама по себе не означает смысловую доказанность.

### Условия, исключения и итоговый вывод

В обосновании отдельно сохраняются дословные выдержки области применения, условий и исключений. Изменённая формулировка «и → или» не проходит как дословная выдержка. Пустое поле условий не считается доказательством отсутствия условий. В ответе показывается полный исходный текст использованного chunk, чтобы короткая выдержка не скрывала оставшуюся часть переданного положения.

Предлагаемый моделью вывод сохраняется в `validation.proposed_conclusion`; итог программы — в `validation.conclusion`. Сама модель не может добавить флаг, что её область применения независимо проверена: такого поля нет в принимаемой схеме.

**Существенный компромисс этого этапа:** независимого семантического проверяющего в проекте нет. Поэтому программа сейчас не выдаёт автоматическое подтверждение соответствия проекта по предложению LLM. Для вопросов о соответствии и сравнений, где применимость/полнота условий не проверены, итог — `requires_clarification`, отображаемый существующим статусом `partial_information`. `compliance_confirmed=false`, `semantic_validation=not_performed` сохраняются явно.

`requirement_found` означает, что найдено и дословно представлено нормативное основание; оно не означает подтверждение соответствия объекта. Новый положительный пример аварийного освещения сохраняет этот статус и текст прямого требования.

Функция `compare_values` поддерживает точное сравнение Decimal с операторами `>=`, `<=`, `=`, `>`, `<`. Она возвращает `satisfied / violated` только если вызывающая сторона независимо установила точность, применимость и обязательные условия. В текущем автоматическом контуре такого удостоверения нет: передаются ложные флаги, результат — `not_established`. Функция проверена локально для `1,00 < 1,05`, но это **не реализация полной автоматической экспертизы применимости норм**.

Свободный ответ старого формата совместим с сервисом, но не публикуется как доказанный нормативный вывод: вместо его непроверенного толкования выводятся исходные цитируемые chunks и требование уточнения. Это влияет на полноту и удобство новых ответов старого формата; изменение сделано явно, а не скрыто за прежним статусом «найдено требование».

### Retry и учёт

Сохраняется одна политика: максимум две генерации на вопрос, обычный случай — одна. Невалидный JSON/ID/выдержка допускает один corrective retry; prompt требует ту же JSON-схему. Отсутствующее во всём контексте измеряемое значение по-прежнему вызывает `ContextValidationError` без повторной генерации. Дополнительных LLM-вызовов для проверки, перевода или оценки нет.

Существующий учёт tokens/calls сохранён, включая оплаченный ответ, отвергнутый проверкой. В тесте исправления malformed JSON учитываются обе генерации. Реальную стоимость нового prompt и устойчивость формата на GigaChat пока не измеряли.

## 3. Совместимость JSON, checkpoint/resume и CLI

Поле `answer` остаётся строкой; прежние поля источников, идентификаторы, конфигурация и CLI-команды сохранены. `validation` — добавочное необязательное поле со значением по умолчанию `None`. Версия checkpoint не менялась, миграция старых файлов не требуется.

Новые результаты проверки сохраняются вместе с ответом в analysis/checkpoint. При resume готовые ответы и это поле не обрабатываются заново. Старые завершённые ответы без `validation` загружаются и сохраняют свой исторический текст и статус; новый отчёт помечает отсутствие новой проверки. Прошлые файлы на диске не переписываются и их статусы не корректируются автоматически.

Сохранённый в runtime ответ прежнего формата при незавершённой операции обрабатывается локально в консервативном режиме без дополнительного API-запроса только ради формата. Проверка provider/model и механизм pause/resume остаются прежними.

## 6. Ограничения и оставшиеся задачи аудита

Достоверно реализованы: происхождение выдержек и чисел, их привязка к конкретным основаниям, единицы/размерности, неизвестные и групповые SOURCE IDs, запрет публикации непроверенного соответствия, сохранение исходных логических формулировок в выводимом тексте и прослеживаемый Markdown.

Автоматически НЕ доказаны: принадлежность нормы обсуждаемому объекту, полнота условий/исключений, правильность выделения модели отдельных полей и оператора, совместное применение нескольких норм, действительность редакций, исчерпывающее раскрытие вопроса и юридическое соответствие проекта. Дословная цитата и номер пункта доказывают происхождение текста, но не эти свойства. Для них нужна экспертная проверка либо отдельно оцениваемая семантическая проверка; простой keyword matching в качестве доказательства не добавлен.

Не решены retrieval-пропуски аудита: специальный пункт кладовых, ограничение смежности лифта и жилой комнаты, условия входных пандусов, высота выхода и правила общих вентиляционных каналов. Не менялись отбор пяти chunks, служебные страницы в кандидатах, формирование search_terms, целостность таблиц/родительских пунктов и актуализация корпуса. Вопросы, которым не хватает контекста, по-прежнему требуют следующего отдельного этапа улучшения поиска.

GigaChat API, detection, генерация ответов на реальной модели, обработка аудио и переиндексация во время задачи не запускались. Поэтому рабочий API-формат и latency нового prompt подтверждены только mocks; реальный текстовый regression run должен быть отдельно разрешён пользователем.
