# Evaluation контрольной записи: текст, говорящие и нормативные вопросы

Evaluation читает сохранённые analysis/progress. По умолчанию не выполняются ASR,
pyannote, embeddings, retrieval, detection или вызовы LLM. Диаризация остаётся
обязательным этапом production; меняется только способ проверки её результата.

## Ручная проверка без временной разметки

1. Откройте `results/ground_truth_review.html` в браузере.
2. Загрузите исходный `data/audio/construction_meeting.wav`. SHA-256 проверяется.
3. Прослушайте запись, исправьте фактические слова каждой из 27 реплик, выберите
   эталонного говорящего и отметьте checkbox проверки. Метки: REF_SPEAKER_01 —
   проектировщик, REF_SPEAKER_02 — руководитель проекта.
4. Подтвердите наличие и корректность восьми нормативных вопросов. Последнее
   перечисление тем не является восемью дополнительными вопросами.
5. Подтвердите полную проверку, экспортируйте JSON и замените им
   `datasets/construction_meeting.json`. Браузер скачивает файл, а не записывает
   его непосредственно в проект. Черновик можно сохранить локально в браузере.

Не нужно размечать start/end, речевые интервалы, DER или нормативные источники.
Не подтверждайте неразборчивые места. Если вопрос отсутствует или сценарий
существенно нарушен, не подтверждайте его: необходимо документировать отклонение,
а не заставлять реальную запись соответствовать сценарию. Нельзя копировать
оцениваемую стенограмму как эталон.

## Формат

Версия schema остаётся 1; новые поля дополняют прежний формат:

```json
{
  "reference_transcript": "Последовательный подтверждённый текст",
  "reference_utterances": [
    {"id": "REF_TURN_001", "text": "Фактически произнесённые слова",
     "speaker": "REF_SPEAKER_01", "confirmed": true}
  ],
  "reference_issues": [
    {"id": "REF_ISSUE_001", "question": "Независимый эталонный вопрос",
     "confirmed": true, "match_concepts": [["эвакуацион"], ["выход"]],
     "expected_sources": [{"document": "Название", "page": 18,
                           "chunk_id": "filename.pdf:p18:c80"}]}
  ],
  "matching": {"mode": "text", "threshold": 0.2},
  "speaker_attribution": {"min_word_coverage": 0.5},
  "verification": {"status": "verified", "audio_sha256": "SHA-256 исходного WAV"}
}
```

Для construction_meeting список содержит 27 реплик и восемь вопросов. Transcript
собирается из текстов реплик в их порядке и должен им точно соответствовать.
`verification.status=pending` блокирует все метрики качества, но не performance.
`verified` требует подтверждения всех реплик и вопросов. Значение устанавливает
человек посредством HTML, а не evaluator после просмотра hypothesis.

## Методы и ограничения

### WER/CER

Обычный Levenshtein: WER=(S+D+I)/N, CER по символам без пробелов. Сохраняется
прежняя нормализация: нижний регистр, пунктуация заменяется пробелами. Ё и е,
цифры и числительные словами не приравниваются. Нормализация не подгонялась.

### Speaker Attribution Accuracy

Сопоставление не использует границы эталонных реплик. Сохранённые сегменты
pipeline идут в хронологическом порядке; start используется только для порядка,
но отклонения start/end не оцениваются.

1. Тексты всех reference-реплик и hypothesis-сегментов превращаются в две
   последовательности слов с прежней нормализацией.
2. Полное Levenshtein-выравнивание выполняется детерминированно. При равной цене:
   диагональ (совпадение/замена), удаление, вставка. Для определения говорящего
   используются только точно совпавшие пары слов. Поддерживается разбиение
   одной reference-реплики на несколько сегментов pipeline.
3. Реплика сопоставлена, если точно выровнено не менее 50% её reference-слов.
   Говорящий должен получить строго больше половины голосов совпавших слов.
   Ничья или отсутствие большинства означает ошибку атрибуции сопоставленной
   реплики. Неизвестные speaker labels не превращаются в известную роль.
4. SPEAKER_00/01 — анонимные метки кластеров. Для всего совещания выбирается
   единое взаимно однозначное соответствие hypothesis labels и reference-ролей,
   максимизирующее число верных сопоставленных реплик. Ничьи разрешаются по
   отсортированным меткам. Нельзя менять соответствие для каждой реплики.
5. Accuracy = correct / matched. Отдельно выводятся total reference, matched,
   unmatched, correct, incorrect, matching coverage и диагностика каждой реплики.

Метрика оценивает согласованность разделения голосов после устранения произвольной
нумерации кластеров; она не доказывает самостоятельное распознавание профессии
или личности. При низком matching coverage accuracy нельзя интерпретировать
без показателя охвата. Ошибки ASR влияют на возможность сопоставления.

### Detection без времени

Ни start/end, ни ответы LLM, ни найденные источники не участвуют в matching.
Используются только независимый reference question и normalized_question
детектора. Косинус сравнивает частоты символьных триграмм нормализованных текстов.
`match_concepts`: AND между группами, OR между префиксами слов внутри группы.
Это фиксированные признаки темы, подготовленные по сценарию. Они различают,
например, количество выходов, высоту проёма и ширину лестницы.

Для construction_meeting порог 0.2 установлен до расчёта новых метрик; он не
является прежним порогом IoU 0.5. Порог относится к другой величине и хранится
в dataset. Ребро допускается при выполнении всех concept-групп и достижении
порога cosine. Максимальное взаимно однозначное сопоставление даёт TP; оставшиеся
predictions — FP, references — FN. Порядок кандидатов: score по убыванию, затем
индекс prediction; проход references в порядке dataset с augmenting paths.
Повтор одного вопроса не даёт дополнительный TP. Выводятся пары, scores и пропуски.

Это воспроизводимое текстовое приближение к совпадению темы, а не полноценная
проверка смысла: отрицания, числа и составные вопросы могут потребовать отдельного
экспертного анализа. Метод не использует обученную модель или LLM-as-a-judge.
Правила и эталон нельзя корректировать после просмотра метрик ради их улучшения.

### Retrieval

После текстового matching берётся сохранённый ranking соответствующего
prediction. Предпочтение `progress.prepared.context_sources`; иначе сохраняется
пометка о reranked candidates из analysis. Источники сравниваются точно по
document/designation и заданным page/chunk_id. Несколько expected_sources —
допустимые альтернативы; Hit не доказывает полноту нормативного ответа.

Hit@1/3/5 и MRR считаются для сопоставленных вопросов с доступным ranking.
Отдельно выводятся evaluated/provided queries и query coverage; несопоставленные
вопросы не маскируются. Они уже являются FN detection, а не автоматически
ошибками поисковика. MRR относится к сохранённой глубине списка, не всему корпусу.

### Производительность и совместимость

Времена ASR/диаризации/detection/retrieval/answers/total читаются из сохранённого
baseline. Длительность берётся из сохранённых metadata или WAV header.
ASR RTF=ASR time/audio duration, Full RTF=total time/audio duration для полного
невозобновлённого запуска. Оценка не запускает заново дорогие модели.

Старые datasets без новых полей поддерживаются: time/segments matching,
reference_diarization и DER сохраняются для прежних экспериментов. Если задан
reference_utterances, вместо DER используется Speaker Attribution Accuracy.
Для construction_meeting DER не вычисляется, точные интервалы не требуются.
Template и production timestamps не меняются.

## Команды из корня проекта

```powershell
.\run-direct.ps1 -m evaluation.run --dataset evaluation/datasets/construction_meeting.json --output-dir evaluation/results/construction_meeting_content
.\run-direct.ps1 -m pytest evaluation -q --reliability-output evaluation/results/evaluation_content_tests.json
```

Без `--dataset` команда сохраняет прежнее поведение и читает template.
Не используйте старый output-dir baseline для нового отчёта. Результаты:
summary.json, CSV основных метрик, speaker_attribution.csv с каждой репликой,
retrieval_queries.csv. Reliability из прежнего отчёта не является новым SLA.
Опциональный legacy `--live-retrieval` не нужен для этого эксперимента и в данной
задаче не запускался.
