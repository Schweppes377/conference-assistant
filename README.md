# Conference Assistant

Проект развивается как набор независимых этапов интеллектуального ассистента онлайн-совещаний.

Реализованы:

1. аудио → ASR (faster-whisper) → диаризация (pyannote) → структурированная стенограмма;
2. нормативные PDF → извлечение текста → chunks → embeddings → локальная ChromaDB → semantic retrieval.
3. текстовый вопрос → semantic retrieval → проверенный контекст → Groq LLM → ответ с источниками.

Контур Question → RAG → LLM работает независимо от стенограммы. Автоматическая обработка реплик совещания, UI, API и real-time относятся к следующим этапам.

Также доступен первый offline end-to-end контур: аудио совещания → стенограмма → выявление нормативно значимых фрагментов с учётом соседних реплик → существующий RAG → grounded-ответы Groq → JSON и Markdown-отчёт.

## Окружение

Проект использует существующее виртуальное окружение .venv. В PowerShell из корня проекта:

~~~powershell
.\.venv\Scripts\Activate.ps1
~~~

Зависимости зафиксированы в requirements.txt. Для PDF используется PyMuPDF, для embeddings — sentence-transformers, для векторного хранилища — ChromaDB.

### Запуск при включённом Happ/VPN

Если Happ включён, запускайте команды проекта через локальный PowerShell launcher:

~~~powershell
.\run-direct.ps1 main.py data\test.wav
.\run-direct.ps1 -m rag.search "требования к эвакуации"
.\run-direct.ps1 -m llm.ask "требования к эвакуации" --debug
~~~

`run-direct.ps1` использует Python из существующего `.venv`, удаляет proxy-переменные только на время запуска дочернего Python и устанавливает для него `NO_PROXY=*`. Это также предотвращает повторное получение SOCKS proxy из Windows WinINET. Для проверки HTTPS используется системное хранилище доверенных сертификатов Windows через `truststore`; TLS-проверка не отключается. После завершения Python исходное окружение PowerShell восстанавливается. Системные настройки Windows и Happ не изменяются, поэтому Codex Desktop, браузер и остальные приложения продолжают использовать VPN/proxy.

## Переменные окружения

Для ASR/диаризации в локальном .env нужна переменная:

~~~dotenv
HF_TOKEN=ваш_токен
~~~

Для Groq LLM в том же локальном .env нужна переменная:

~~~dotenv
GROQ_API_KEY=ваш_ключ
GROQ_MODEL=openai/gpt-oss-120b
~~~

GROQ_MODEL необязательна: по умолчанию используется openai/gpt-oss-120b. Выбранная модель проверяется через Groq Models API, и при её недоступности автоматического переключения не происходит.

HF_TOKEN применяется только для pyannote, GROQ_API_KEY — только для Groq. RAG использует публичную embedding-модель и секретов не требует. Не добавляйте реальные токены в README или Git; .env уже находится в .gitignore.

## Транскрипция аудио

Положите аудиофайл, например, в data/test.wav, затем выполните:

~~~powershell
python main.py data/test.wav
~~~

Язык по умолчанию — русский. Другой язык и автоопределение:

~~~powershell
python main.py data/test.wav --language en
python main.py data/test.wav --language auto
~~~

По умолчанию Whisper использует модель medium и CUDA. При недоступной CUDA предусмотрен CPU fallback.

Тестовый корпус включает:

- СП 59.13330.2020 — доступность для МГН;
- СП 20.13330.2016 — нагрузки и воздействия;
- СП 22.13330.2016 — основания зданий и сооружений;
- СП 63.13330.2018 — бетонные и железобетонные конструкции;
- СП 345.1325800.2017 — проектирование тепловой защиты;
- СП 60.13330.2020 — отопление, вентиляция и кондиционирование;
- СП 30.13330.2020 — внутренний водопровод и канализация;
- СП 52.13330.2016 — освещение;
- СП 275.1325800.2016 — звукоизоляция;
- СП 48.13330.2019 — организация строительства.

Основной источник строительных СП — официальный реестр ФАУ «ФЦС» Минстроя России; пожарные СП получены с официальных ресурсов МЧС России. Файл FZ_384_amendments_2023.pdf является сканом без текстового слоя. OCR на текущем этапе не выполняется, поэтому индексатор его пропускает.

## Добавление PDF

1. Скопируйте читаемый PDF в data/documents/.
2. Добавьте запись о нём в data/documents/sources.json: имя файла, название, обозначение, официальный URL, редакцию и статус.
3. Повторно запустите индексацию.

Если записи в каталоге нет, индексатор использует имя файла как временное название и выводит предупреждение. Повторная индексация заменяет chunks этого файла, а не создаёт дубликаты.

## Индексация

Из корня проекта:

~~~powershell
python -m rag.index
~~~

По умолчанию используются:

- embedding-модель intfloat/multilingual-e5-small;
- cosine distance;
- chunk size 1200 символов;
- overlap 200 символов;
- локальное хранилище data/chroma/;
- CUDA, если она доступна, иначе CPU.

Первый запуск загружает embedding-модель в локальный кэш. Параметры можно менять:

~~~powershell
python -m rag.index --chunk-size 1400 --chunk-overlap 250 --batch-size 24
python -m rag.index --model intfloat/multilingual-e5-base
~~~

При смене embedding-модели используйте новый --persist-dir или удалите старый индекс вручную после того, как убедитесь, что он больше не нужен.

## Семантический поиск

~~~powershell
python -m rag.search "требования к эвакуационным выходам в многоквартирном доме"
python -m rag.search "доступность входа для маломобильных групп населения" --top-k 8
~~~

Для каждого результата выводятся score, cosine distance, название и обозначение документа, номер PDF-страницы и текст найденного chunk.

## Question → RAG → LLM

Схема третьего этапа:

~~~text
Вопрос
  → TOP-K semantic retrieval из существующей ChromaDB
  → фильтрация по relevance score
  → полный контекст из найденных chunks и metadata
  → provider-independent LLMClient
  → Groq Chat Completions
  → ответ + проверенные источники из ChromaDB metadata
~~~

Запуск:

~~~powershell
python -m llm.ask "Какие требования предъявляются к эвакуационным выходам в многоквартирных жилых зданиях?"
~~~

Расширенная диагностика retrieval, latency и token usage:

~~~powershell
python -m llm.ask "Какие требования предъявляются к эвакуационным выходам?" --debug
python -m llm.ask "Какие требования предъявляются к эвакуационным выходам?" --json
~~~

Проверить модели, доступные конкретному Groq API-ключу:

~~~powershell
python -m llm.ask --list-models
~~~

Настройки по умолчанию:

- модель: openai/gpt-oss-120b;
- кандидатов retrieval до reranking: 20;
- финальных chunks после reranking (TOP_K): 5;
- минимальный similarity score: 0.84;
- максимальный сериализованный контекст: 12 000 символов;
- temperature: 0.1;
- максимальный ответ: 1 200 tokens.

Параметры переопределяются аргументами CLI или переменными GROQ_MODEL,
RAG_CANDIDATE_K, RAG_TOP_K, RAG_MAX_CONTEXT_CHARS, RAG_MIN_SCORE,
LLM_TEMPERATURE и LLM_MAX_OUTPUT_TOKENS. Контекст ограничивается только целыми
chunks: их текст не обрезается и не отделяется от metadata.

Retrieval выполняется в два этапа:

1. semantic search по исходному вопросу и коротким `search_terms`;
2. объединение кандидатов и лёгкий reranking по semantic score, совпадению
   специальных терминов и совместному присутствию объекта и параметра.

В LLM передаются только пять лучших reranked chunks. В структурированном
результате `retrieved_candidates` содержит расширенный список кандидатов, а
`cited_sources` — только chunks, на которые модель действительно сослалась.

LLM получает источники с внутренними идентификаторами SOURCE_1, SOURCE_2 и так далее. После ответа приложение сопоставляет цитаты с реальными title, designation, page и chunk_index из ChromaDB. Неизвестные SOURCE-ID отклоняются.

Если ни один результат не достигает порога релевантности, Groq не вызывается, а программа отвечает:

~~~text
В найденных нормативных документах недостаточно информации для обоснованного ответа на этот вопрос.
~~~

Даже при релевантном контексте system prompt запрещает модели использовать собственные нормативные знания, придумывать документы, страницы, пункты или числовые требования.

Если Happ/VPN включён, используйте `run-direct.ps1`, как описано выше. Программа не изменяет системный proxy/VPN и не выполняет скрытый fallback на другую модель.

## Полный анализ совещания

Запуск offline pipeline при включённом Happ:

~~~powershell
.\run-direct.ps1 -m app.analyze_meeting data\audio\construction_meeting.wav --debug
~~~

Detector анализирует стенограмму окнами соседних реплик, формирует самостоятельные нормативные вопросы, проверяет возвращённые LLM идентификаторы реплик и объединяет дубли. Обычные организационные реплики не должны попадать в RAG. Для каждого вопроса применяется существующий grounded Question → RAG → LLM слой; ошибка одного вопроса сохраняется в результате и не прерывает обработку остальных.

Detector дополнительно формирует `search_terms`, сохраняя точные названия
обсуждаемого объекта и параметра. По умолчанию retrieval формирует до 20
кандидатов (`--candidate-k`), reranking выбирает пять (`--top-k`), и только они
могут попасть в контекст LLM.

Каждый запуск создаёт в `data/results/` три отдельных файла с уникальным timestamp в имени:

- `*_transcript.json` — стенограмма со спикерами и временными метками;
- `*_analysis.json` — вопросы, ответы, статусы, источники, retrieval scores и метрики;
- `*_report.md` — человекочитаемый отчёт.

Статус `potential_noncompliance` означает только потенциальное несоответствие, привязанное к найденным фрагментам, и требует проверки специалистом. Он не является юридическим заключением.

Статус `partial_information` означает, что нормативное требование найдено
частично: например, обнаружено общее требование по шуму, но в доступных chunks
нет конкретных дневных и ночных значений. В Markdown он отображается как
«Нормативное требование найдено частично».

## Тесты

~~~powershell
python -m unittest discover -s rag -p "test_*.py" -v
python -m unittest discover -s llm -p "test_*.py" -v
~~~

Тесты проверяют chunking, отсутствие дублей в ChromaDB, формирование grounded prompt, привязку SOURCE-ID к metadata, недостаточный контекст, недоступную модель, rate limit и отсутствие API-ключа. Аудиоконвейер этими командами не запускается.
